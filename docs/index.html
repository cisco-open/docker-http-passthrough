Docker HTTP Passthrough

A registry-aware HTTP service that turns Docker images into tar archives Cisco devices can retrieve with ordinary copy http workflows.

Route selection

Choose where registry details come from

Use a static default registry, let the request choose the registry, or let the Cisco device provide both registry details and credentials per download.

01

Configured default

The passthrough container supplies registry settings through environment variables. Clients keep using the short /docker/{filename} route.

/docker/nginx_latest.tar
02

Request-selected registry

The request URL carries the registry scheme and host. Useful for GHCR, Docker Hub aliases, or an enterprise registry such as registry2. Credentials can still come from the service when needed.

/registry/https/ghcr.io/docker/org__app_latest.tar
03

Request-selected auth

The service challenges the client with HTTP Basic auth and forwards those credentials upstream for the selected registry request without storing them.

/registry-auth/http/registry2:5000/docker/team__api_1.0.tar

Published OCI image

          
Install the passthrough service from GHCR

          

            The project publishes a multi-arch image for linux/amd64 and
            linux/arm64 at ghcr.io/cisco-open/docker-http-passthrough.
          

        


        

          

            
Docker

            
Run the service directly from the published OCI image.

            docker run -d -p 8080:8080 ghcr.io/cisco-open/docker-http-passthrough:latest
          

          

            
Kubernetes

            
Use the included manifest, which points at the GHCR image by default.

            kubectl apply -f kubernetes.yaml
          

          

            
App-hosting source

            

              Use the GHCR image reference directly where supported, or convert it to a
              Docker save archive with the passthrough route for IOS-XE CLI installs.
            

            ghcr.io/cisco-open/docker-http-passthrough:latest
          

        

      


      

        

          
Topology

          
Cisco device to registry delivery path

          

            The passthrough service sits between network devices and container registries.
            It can run as a Docker container or in Kubernetes while targeting Docker Hub,
            GHCR, or an enterprise private registry reachable from the service.

Device reachability

            
The Cisco device only needs HTTP reachability to the passthrough endpoint.

          

          

            
Registry reachability

            
The passthrough service needs network access to the selected registry host.

          

          

            
Credential scope

            
Authentication mode forwards request credentials for one transfer and does not persist them in the service.

          

        

      


      

        

          
Execution flow

          
From Cisco copy to Docker load

          

            Each request is prepared before a success response is sent, so registry errors
            are returned as HTTP failures instead of partial tar files.
          

        


        

          

            1
            HTTP GET
            
Cisco device or curl requests a tar URL.

          

          

          

            2
            Parse image
            
Filename becomes repository and tag.

          

          

          

            3
            Resolve registry
            
Static config or request-selected target.

          

          

          

            4
            Fetch layers
            
Manifest, config, and blobs are prepared.

          

          

          

            5
            Stream tar
            
Docker save archive returns to the client.

Validation

          
App-hosting paths exercised end to end

          

            The Cisco workflow has been checked from copy http through
            archive storage, app-hosting install, activation, start, status, and cleanup.
          

        


        

          

            
Public pulls

            

              Docker Hub, local registry, and public GHCR images were copied to the
              device, installed, activated, started, and verified in app-hosting.
            

            /docker
            /registry/https/ghcr.io
          

          

            
Authenticated paths

            

              Static service credentials and Cisco-supplied HTTP client credentials were
              both exercised through copy and app-hosting start.
            

            /docker with REGISTRY_CLIENT_AUTH=required
            /registry-auth/{scheme}/{host}
          

          

            
Private GHCR requirement

            

              Private GHCR uses the same authenticated route, but requires a GitHub token
              with package read permission for the target private package.
            

            my-org__private-image_latest.tar
